# T11i: MIDI input on the device

Integration lane for T11 (MIDI in). Wires the T11c core (`core/midi/midi_in.c`) to the TRS/USB
inputs, the LIVE play path, the clip engine and the transport. Runs alongside T10i (`ui_live.c`,
the master path) and T7b (`ui_studio.c`, `ui_clip.c`, `song_io`, the clip engine's recording
hooks). This revision merges `integration` and applies every item in
[T11i-review.md](T11i-review.md). Nothing was flashed.

- New: `firmware/src/app/midi_live.c/.h`.
- Changed: `engine.c` (the ring's consumer, MIDI-in only), `main_fm1.c` (the main-loop poll, the
  boot clock source and the audio ISR's sample-clock anchor), `usb.c` (the 256-slot pool ring, the
  arrival stamps, the overflow policy), `midi_uart.c` (the same push), `plat.h` / `plat_fm1.c`
  (`plat_midi_in` carries the stamp, `plat_sample_now`/`plat_sample_sync`), `ui.c` (the GLOBAL
  `CLOCK IN` row, `midi_live_note_all_off` in the held-note release), `live_bridge.c/.h`
  (`launch_quant`, the transport restart/continue, `set_bpm_soft`), `core/seq/clip_engine.c/.h`
  (Start / Continue, a live tempo), `host/x0x_host.c`, `host/build_host.sh`, `Makefile`,
  `tools/build.py`, `web/emu/build.sh`, scenarios + goldens, and the docs.

## Where the bytes go

T11c's module is fed in the **main loop**, in the same context that calls `midi_in_tick`. This is
required, not just tidy: every path the sink drives — `live_bridge_play_key` (an engine command
through X0X's `cq_put`), the clip engine's launch/transport/BPM ring — is a main-loop API, and
`cq_put` from the audio path traps in the host (`engine.c`'s `in_isr`) and would race the ISR's
own drain on the device. So:

- `midi_live_poll(sample)` (`firmware/src/app/midi_live.c`) drains the shared TRS/USB ring with
  `plat_midi_in`, feeds every packet to one `midi_in_t` with **the producer's own arrival stamp**,
  calls `midi_in_tick`, follows the tempo and updates the EXT flag. `main_fm1.c` calls it once per
  main loop; the host runner once per simulated millisecond.
- **Stamps at the source (review 1).** The producer (`usb.c`'s endpoint read, `midi_uart.c`'s
  `um_put`, both in the TIMER5 ISR) writes each packet into a timestamped ring. The stamp is
  `plat_sample_now()`: the audio ISR anchors the pair (block start, 24 MHz timer) at each half in
  `render_block`, and between them the timer extrapolates, under a seqlock (TIMER5 preempts the
  render). A stalled main loop draining a batch therefore feeds the true arrival times instead of
  one stamp for the whole batch; `midi_live_poll` ticks on the same clock.
- In **Classic** `live_bridge_active()` is 0, `midi_live_poll` does nothing, and `engine.c`'s
  `drain()` keeps consuming the ring for X0X's own per-part channels and clock, exactly as before.
  `engine.c` gained one `if (!live_bridge_active())` around its existing ring loop.
- **One instance.** The ring stores USB-MIDI packets and does not tag the source (TRS is packed
  into the same `midi_in_q`), so TRS and USB share one `midi_in_t`; two would need the ring to
  carry a cable/source tag. `midi_in_packet` decodes cable 0 and the CIN, so both work.
- **Ring overflow (review 4).** The input ring is 256 slots **in the pool** (a busy USB host can
  burst a 64-packet frame at once), each with its stamp. Below 16 free a **note-on** is dropped
  first, so a note-off always has room; a packet dropped with the ring truly full sets an overflow
  flag, and the next poll runs `midi_live_note_all_off()` for the app's held notes, so a lost
  note-off cannot hang. The update loader compiles `usb.c` with `FELUCCA_LOADER`, which keeps the
  original 64-slot rings and the original endpoint write, so the loader stays byte-identical to
  X0X 1.0.5 (`tools/check_loader.sh`).

## Routing (config from the song)

`midi_live_poll` re-reads `song.live_channel` / `song.pc_launch` / `song.quant_default` every call
via `live_bridge_song()`, so a song load or a LIVE SETUP edit takes effect with no hook.

- **Notes** on the live channel (0 = omni) play the focused role (`live_focus()`, the same focus the
  PLAY layer uses) through `live_bridge_play_key`, velocity included. They work in STUDIO and LIVE;
  in Classic X0X's channels stay.
- **Held notes.** A `uint8_t mh[128]` maps each note to the role it was played on, so a note-off
  releases the role it started on even if the focus moved (and a re-strike after a focus move frees
  the old role). `note_release_all()` (the view, layer and mode changes) now also calls
  `midi_live_note_all_off()`, and entering Classic resets the table (the engine's all-off already
  silenced the voices). The overflow release is the same call. This keeps the "no hung notes"
  invariant.
- **Program Change** (when `pc_launch`) launches clip = program (0..26) through a new
  `live_bridge_launch_quant(clip, quant)` at the song's `quant_default`; the core already ignores
  programs >= 27 and the sink guards again.
- **CC 120 / 123** release every MIDI-held note and call `engine_all_off()`.
- **Transport (review 2).** 0xFA **Start** calls `live_bridge_transport_restart()`:
  `clip_engine_restart` forces bar 1, step 0 and relaunches what was playing (the clips a stop
  saved). 0xFB **Continue** calls `live_bridge_transport_continue()`: `clip_engine_continue`
  resumes the clip and the position from the stop point. 0xFC **Stop** is
  `transport_stop`. F2 (SPP) is parsed but the clip engine has no seek, so it is **not wired**
  (documented here and in the interaction model).
- **Clock.** `midi_live_tick` follows `midi_in_bpm_x10` while `midi_in_clock_ok`, sending the tempo
  through `live_bridge_set_bpm_soft` (a **live** tempo, `CLIP_CMD_SET_BPM_SOFT`) only on a real
  change (>= 0.5 bpm). The soft path never writes `song.bpm_x10`, so the song's own tempo survives
  the clock. When the clock stops the last tempo stands and the EXT flag clears.

## GLOBAL `CLOCK IN`

A new GLOBAL row, `CLOCK IN` = `AUTO` (default) or `INTERNAL`, stored in `proj.set.rsv[1]`
(`rsv[0]` is T8i's song slot; the stored size and format are unchanged, so an older settings
object loads AUTO). `AUTO` follows the incoming clock; `INTERNAL` drops the system messages at the
feed, so neither the tempo nor the transport is taken, and **restores the song's own `bpm_x10`**
(review 3) — `midi_live_tick` re-sends the song tempo (which the soft path kept intact) through the
normal `live_bridge_set_bpm`. The row sits after `CLOCK OUT`, which shifted the GLOBAL list down
one; five scenarios that navigate the list by index were updated (+1) and `studio_classic_exit`'s
golden sample counter moved by the one extra turn detent.

Per the coordinator, the header's **EXT** chip and the LIVE SETUP rows for the live channel /
Program Change are **not** drawn here: `midi_live_ext()` (following an external clock) and
`midi_live_bpm_x10()` (the followed tempo) are exposed for the coordinator to draw the chip after
T7b/T10i land, and the LIVE SETUP rows are a follow-up task. The host runner sets the two song
fields directly for the tests; SPP is unsupported (documented above).

## Tests

Seven scenarios, each with a dump golden (`tests/scenarios/midi_*.x0x`, `tests/golden/midi_*/`).

| Scenario | Checks |
|---|---|
| `midi_notes` | omni vs a fixed channel; notes play the focused role and release; FM6 back to zero voices |
| `midi_launch` | PC launch on the bar; out-of-range PC and a PC on another channel ignored; CC 123 and CC 120 release all |
| `midi_clock` | 25 F8 ticks at 100 bpm set the tempo and start the transport; clock lost keeps playing at 100 with EXT off; Stop and Continue; `CLOCK IN = INTERNAL` ignores the clock and the transport and restores the song's 125 bpm; AUTO follows 120 bpm |
| `midi_hold` | a note held across a view change is released; a note re-struck after the focus moved frees the old role; the late note-off is harmless; then `midifuzz 12345 300` (random notes / PC / CC across all 16 channels, then the panic) leaves no held note and no T5i voice |
| `midi_transport` | Start relaunches the clip from bar 1 step 0; Continue resumes the clip and the position from the stop point |
| `midi_stall` | 64 queued ticks survive a 20 ms main-loop `stall` (no poll): the drain reads the stored stamps, so the tempo is still 120 |
| `midi_overflow` | `midiflood 300` overflows the ring; no note hangs (the overflow releases every held note) |

The runner's new MIDI commands: `midicfg CHANNEL PC`, `midiclock BPM N` (queues N ticks with
arrival stamps), `stall MS` (a busy main loop: audio runs, no MIDI poll), `midiflood N`,
`midifuzz SEED N`; new expect keys `bpm`, `midibpm`, `ext`, `midiheld`.

`make unit-midilive` ports the reviewer's `clk2.c`: it drives the real `midi_live` with a fake
producer that stamps every tick at its arrival, and a consumer at 8 / 12 / 20 ms a frame with a
20 ms stall, at 120 and 174 bpm. The followed tempo stays exact (bpm_x10 1200 and 1739, within the
+/-10 requirement). It runs in `make unit-core` and under ASan/UBSan.

## Notes / decisions

- **One instance, one context.** The ring is SPSC; in STUDIO/LIVE the main loop is the consumer and
  the TIMER5 ISR (USB / TRS) the producer. The producer stamps, so the two clocks are one.
- **The clock's tempo is transient.** `clip_engine_queue_bpm_soft` sets the running tempo without
  writing `song.bpm_x10`; a UI tempo change (the normal path) cancels it. `clip_engine_continue`
  and `clip_engine_restart` are additive; the PLAY button still uses `clip_engine_start`.
- **A MIDI-held table, not the key table.** `ui.c`'s table is keyed by key (0..26); external notes
  are arbitrary and not tied to keys, so `midi_live` keeps its own note -> role table and is
  released by the same `note_release_all` path.
- **The loader is untouched.** `usb.c` keeps the X0X 1.0.5 code under `FELUCCA_LOADER`, so the
  update loader's image and hash are unchanged.
