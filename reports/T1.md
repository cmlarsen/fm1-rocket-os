# T1: build X0X remotely and strip BREAK

Branch `cmlarsen/t1-import`, started from `integration` (base `5210983`). Five commits: the
Makefile/release/loader guard, then the BREAK strip in three parts (firmware, tests, tools/web),
then the docs/licensing, then dropping the QEMU target. Nothing was flashed.

## What I did

1. **Toolchain on deltron.** Copied `tools/get_toolchain.sh` and ran it (JieLi
   `jieli-linux-toolchains-20260730.1` in `~/.jieli/toolchain`); cloned the AC79 SDK
   (`AC79NN_SDK_V1.2.1_2023-12-13`) to `~/fw-AC79_AIoT_SDK`; cloned the reference sources the
   `tests/host/run_*.sh` scripts look for next to the remote build tree (`~/fm1-build/schwung-303`,

   `clean-remote`. `fw` brings back `x0x.fwsc`, `x0x.bin`, `loader/ota.bin`; `test` returns
   `tests/run_tests.sh`'s exit code and brings back `build/scenarios/`.

## Release comparison (step 3)

`gh release list` → the real tag is `v1.0.5`; the asset is `x0x-1.0.5.fwsc`. The release was a
release build: its identity is `FM-1_9010005` (the `make fw` dev build is `FM-1_900`). Rebuilt on
deltron from the untouched tree:

```
make release VERSION=1.0.5     ->  build/x0x-1.0.5.fwsc
sha256  080b190761e4a3389a97a19be05dbc1c5890d0fa6addd9af0e66227667a052f9
```

**Byte-identical to the downloaded `x0x-1.0.5.fwsc`.** `make fw` (plain `./build.sh`) differs only
in the identity string and the version (`FM-1_900` / `DEV` vs `FM-1_9010005` / `1.0.5 BETA`); its
`loader/ota.bin` is identical to the release's. So the difference between `make fw` and the release
is exactly the release recipe, nothing else.

## The BREAK strip (step 5)

Removed entirely: `firmware/src/dsp/breaks.{c,h}`, `tools/{gen_break_bank.py,gen_builtin_break.c,
gen_builtin_break.sh,import_breaks.py,upload_breaks.py}`, `tests/host/{breaks_test.c,run_breaks.sh,
emu_slots_test.mjs,make_test_loops.py}`, `web/{test_breaks.mjs,x0x_breaks.html,x0x_breaks.js}`,
`docs/img/screen-break.png`, `.github/FUNDING.yml`, and the break scenarios `slices.x0x`/`upload.x0x`.
Every reference went with them: the pattern model, the sequencer's fifth track and `brk`/`brk_stop`
sinks, the engine's break state/command/mixer/loops/PERF stage, the UI's BREAK screens/keys/pages/
settings, the WASM slot uploader, the manual/site/mix tools, and the docs.

**Storage format kept (as the task asked).** `pattern_t`'s `brkpart_t brk` becomes
`uint8_t rsv_part[36]` (`RSV_PART_N`), same size and offset. `NTRACKS` is 4 with a reserved
`song_bar_t` byte (so the song's mute byte stays at offset 5), and the new `T_RSV` enum keeps
`sound_t`'s size. `pattern_t`, `song_t`, `sound_t`, `settings_t` and the packed stream's `RAW_LEN`
are unchanged, and the format-1 loader's `rsvpart1_t` keeps its 20 bytes, so projects saved by X0X
still load — the `migrate` and `migrate0102` scenarios pass on the `v1_store.bin`/`v0102_store.bin`
fixtures. (`NPARTS` is 4; the last `settings_t.midi_ch` byte is reserved.)

## Verification (step 7)

- **`make fw` builds on deltron.** Image 456504 B (was 580372), `.ram_text` no calls, **no
  soft-double routines**, RAM `.data+.bss` 95044 B of 98304, pool 328052 B of 344064, loader
  6524 B, package 609680 B.
- **No BREAK symbols.** `strings -a build/x0x.bin | grep -iE 'break|brk'` → nothing (and the same
  on the `.fwsc`).
- **`tools/check_loader.sh build` passes** after the strip.
- **Host tests.** On the Mac (Apple clang; reference checkouts pointed at with
  `TB3PO_REF`/`SCHWUNG303`/`EIGHTW8_DIR`/`NINEW9_DIR`), `tests/run_tests.sh` prints **all tests
  passed** — every unit test, every engine reference comparison, `storage`, `installer`, the host
  build and all scenarios. Skipped on the Mac: `update-loader` (no `AC79_SDK`) and the
  WASM/`emu` test (no Emscripten).
- **`make test` on deltron** passes every suite **except `bass303`** (see below).
- **WASM parity was not run.** Node is on the Mac (v26.8.1) but `emcc` is not, so `build/emu/x0x.wasm`
  cannot be built. The WASM build uses the same `host/` sources that pass, and `tests/host/emu_test.mjs`
  is unchanged.

## What did not work / needs attention

- **`bass303` on deltron (gcc) fails; it passes on the Mac (clang).** `BASS303_OS=4`'s spectral
  centroid for `reso+envmod` and `square+accent` is 10.4% and 13.1%, just over the test's 10%
  (`CEN_MAX`) tolerance; `BASS303_OS=2` passes. This is a compiler sensitivity in the port-vs-
  Open303 comparison, **unrelated to the BREAK strip** (`bass303.c` is untouched). I did not loosen
  X0X's tolerance. T1's acceptance ("X0X tests … pass unchanged on the Mac") holds.
- **Two small Linux portability fixes were needed** for `make test` on deltron and are committed:
  `-D_GNU_SOURCE` for the host simulator (`host/build_host.sh`) and the bass303 reference test
  (`tests/host/run_bass303.sh`), for `clock_gettime`/`M_PI` under `-std=c99`.
- **`make emu-binary` (step 8) was skipped** on the coordinator's instruction. Separately, the
  current `fm1-emulator` cannot boot X0X: it accepts only SPI1 `BAUD=4`, and X0X's `lcd.c` sets
  `LCD_BAUD 0` ("SPI1 supports idle BAUD 4 only at PC 0x0201040a"). Felucca 1.5 boots in the same
  emulator, so the emulator itself is fine; the LCD baud (or an emulator change) is the blocker. No
  half-working target was committed.
- **Historical docs.** The project's own records that describe the strip keep their BREAK mentions
  (`docs/engineering/build-plan.md`, `tasks/T1.md`, ADR-0001, `roadmap.md`, `fork-evaluation.md`,
  `firmware-landscape.md`, the build-plan review). X0X's user docs and dated plans are cleaned.
