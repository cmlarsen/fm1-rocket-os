## Behaviour
- **Byte parser** for one stream (TRS and USB each get an instance):
  - running status;
  - real-time bytes interleaved anywhere, including inside other messages;
  - SysEx passed over without corrupting state;
  - Note On with velocity 0 treated as Note Off;
  - USB-MIDI 4-byte event packets are also accepted (decode the cable and the code index).
- **Routing**, driven by a config struct taken from the song:
  - notes on `live_channel` (1–16, or 0 = omni) go to a "play note" callback with velocity;
  - **Program Change** on the live channel, when `pc_launch` is set, launches clip number = program (0–26), quantized, through a launch callback. Out-of-range programs are ignored.
  - CC 120/123 release all notes.
- **Clock follow:**
  - 0xF8 ticks give the tempo as a smoothed estimate, `bpm_x10` with integer math, steady within ±0.5 bpm of jitter-free input. It reacts to a tempo change within 1 beat.
  - 0xFA start, 0xFB continue and 0xFC stop go to transport callbacks.
  - Song Position Pointer is accepted and passed to a callback.
  - When ticks stop for longer than 1 beat at the last tempo, a "clock lost" callback fires.
- **Context:** the parser runs wherever X0X receives bytes. Timestamps are sample-counter values the caller passes with each byte or packet. No heap, no `double`, no 64-bit division, constant time per byte.

## Tests (write first)
Write `tests/host/midi_in_test.c`, with a sanitizer build too. It covers:
- running status;
- real-time bytes inside a note message;
- SysEx with notes before and after it;
- velocity-0 note off;
- USB packets;
- channel filter and omni;
- PC launch, including out of range;
- CC 123;
- clock at 60, 120 and 200 bpm with ±1 ms jitter, where the estimate stays within ±0.5 bpm;
- a tempo ramp;
- start, stop and continue;
- clock lost;
- random byte fuzzing for 1,000,000 bytes: no crash, and state recovers on the next status byte.

Compile the files for the device on deltron and report the code and RAM sizes.
